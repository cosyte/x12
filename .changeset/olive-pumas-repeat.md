🩺 Two 837 mis-attributions corrected: a trailing line-level segment after a dropped `LX` does not land on the last named party, and `X12_837_UNKNOWN_VARIANT` points at the `ST` rather than the `BHT` (`X12-837-LOOP-RESIDUALS`).

Both of these are mis-**attribution** rather than loss. **No warning CODE is added, removed, widened or narrowed by either**, on every case measured. What moves is where a value, or a warning, is said to be. Be precise about that second one: the variant warning's `position` is exactly what changed, so the emitted codes are identical while one emitted position is not. That is why neither minted a new warning code.

**A `REF` / `N3` / `N4` / `PER` after a dropped `LX` does not attach to the last named party.** Through `0.0.10`, the release published as this was written, an `LX` arriving with **no `CLM` open** reported the dropped service line and then left the previous `NM1`'s party still addressable. Because the payer accumulator is what the **next** `CLM` opens against, the values surfaced on a **later claim**: measured, a line-item control number in `payer.references`, a street address in `payer.address`, and a contact in `payer.contacts`, none of which the sender put there. On that route all seven of `DTP` / `AMT` / `NTE` / `REF` / `N3` / `N4` / `PER` are discarded; the `DTP` / `AMT` / `NTE` already were at `0.0.10`, and the other four are what changed. Retention is unchanged and the segments stay verbatim on `tx.segments`.

**This is a trade, and the cost is that a conformant entity segment can now be dropped.** The TR3s nest Loop 2400 inside Loop 2300 and say nothing about an `LX` elsewhere, so which party a segment following a **stray** `LX` belongs to is not derivable from the spec in either direction. Where the `LX` was injected into an **entity** loop, the segments after it really were that entity's: measured, a payer that kept its `PO BOX` address, its `2U` secondary id and its contact at `0.0.10` now comes back with `address: undefined`, `references: []` and `contacts: []`. The direction was chosen because a mis-attribution puts a value on an object the sender never put it on and is indistinguishable from real data, whereas the bytes of a discarded segment are still on `tx.segments`. **That discard shipped SILENT in this change and no longer is:** each such `N3` / `N4` / `PER` / `REF` raises `X12_837_ENTITY_SEGMENT_DISCARDED_AFTER_LX`, added in a follow-up change that is unreleased alongside this one, so no published release ever had the discard without the warning. `X12_837_SERVICE_LINE_DROPPED` at that `LX` still reports the **service line** and not an entity's address, id or contact, so it never named this loss. The loss itself is unchanged and is still pinned by tests.

**The route-dependence survives and still has to be read.** With a `CLM` open, a trailing `DTP` / `AMT` / `NTE` / `REF` still lands among the claim-level ones. Only the no-claim route moved, and it is no longer split within itself.

**If you parsed with `0.0.10` or earlier and relied on an entity's `address`, `contacts` or `references`, those slots could be carrying line-level values from a dropped Loop 2400.**

**`X12_837_UNKNOWN_VARIANT` anchors at the `ST`.** Its `position.segmentIndex` was `1`, which in a transaction-scoped position is `tx.segments[1]` and in an 837 is the `BHT`, a segment with no part in resolving a variant. It is now `0`, the `ST`, which carries the ST-03 the resolution reads. A consumer joining this warning back to the document gets a different segment than it did on `0.0.10`. No `elementIndex` is set, deliberately: one of the two routes into this warning is an ST-03 that is absent entirely, and there the `ST` is `["ST", "837", "0001"]` with no element 3 to name.

**Deliberately not in this change.** An absent `SV1-02` on a line that DID open still reads a confident `0`; that closes only with the deferred `X12Decimal | undefined` model change. With no caller `type` and an `ST-03` outside the three known implementation conventions, variant resolution still falls back to the first `SVx` anywhere in the transaction body, orphans included, so one stray `SV2` re-types a whole submission; that is pre-existing, warned rather than silent, and narrowing it would change how already-published documents decode. `KNOWN-LIMITATIONS.md` states both.

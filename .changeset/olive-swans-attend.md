Repository PHI commit-gate only, with no runtime impact: the all-mode `phi-scan` sweep can no longer report clean over the files it never opened within its declared roots.

No library code changed, no public type changed, and nothing a consumer installs behaves differently. It is recorded here because a gate that attests clean over bytes nobody read is worth a changelog line even when the package itself is untouched.

`pnpm phi-scan` with no arguments walks two roots, `test/fixtures` and `src`, and prints `OK - no hits` at exit 0 when it finds nothing. Finding nothing and opening nothing were indistinguishable. Each shape below was measured on a throwaway repository laid out like this one, against a synthetic `.edi` payload whose person name, date of birth, contact phone and SSN qualifier are hits at exit 1 when the same bytes are actually read:

- with both walk roots absent, and with `test/fixtures` alone absent, the walk returned immediately and the sweep printed `OK - no hits` at exit 0. A root a repository never had is the worst shape of it, because the gate then reads clean on every run it ever makes and no run looks wrong;
- with the roots present but emptied on disk while their files stayed in the index, the sweep printed `OK - no hits` at exit 0 over a corpus whose committed bytes are hits;
- with a walk root replaced by a regular file, the directory read threw an unhandled `ENOTDIR` and the process ended at exit 1, which is this scanner's own code for "hits found", as a stack trace rather than a refusal. A root that is a named pipe ended the same way. That exit code is not portable between packages and neither is the mechanism, so it was re-measured here rather than carried over from a sibling.

The remedy is two rules, and the second is not implied by the first, because existence is not observation. A declared walk root must be a directory, and every tracked, non-markdown file under a root must have been one of the files the walk actually enumerated. Both refuse at exit 2 and name every offender, and each is independently load-bearing: dropping the first reds four of the new cases, dropping the second reds five, and the two sets are disjoint. Naming every offender needs one more thing than the rule itself: git returns an unmerged path once per merge stage, so the index listing is deduplicated, or a single conflicted fixture is named three times and counted as three. That flag is pinned by its own case. A refusal here also never echoes git's own message, because the child's stderr in this class carries absolute filesystem paths and a diagnostic about a PHI gate is itself a PHI surface; only the exit status is reported.

Say "be a directory" and never "be enumerable". A draft said the second and it was measured false: a root that IS a directory the process cannot open passes the type check and then throws an uncaught `EACCES` out of the directory read, at exit 1, identically before and after. An unreadable subdirectory under a root ends the same way. That class is pre-existing, disclosed, and deliberately not closed here, because closing it means tolerating or classifying a failed directory read, which is a separate deferred remedy pulling the same way. The claim was cut back to what the code checks rather than the guard grown.

A root that is itself a symbolic link to a directory is still followed, as before, and where that link is tracked the reconciliation exempts the root's own index entry: `git ls-files` returns the link's own path while the walk only ever yields paths under it, so comparing the two would refuse over a tree that is scanned as a documented superset. A draft added that it opens no clean path, because a root that is a tracked regular file, or a link to one, is refused by the root check first. That is true and it is not the whole of it, so the claim is cut back rather than the guard grown: when a root is a tracked link to a directory, everything the walk reads through it lives under the target's own names, outside the pathspec the reconciliation asks git for, so the whole link-target corpus is unreconciled. Measured at head, a committed payload under such a target, removed from disk but still in the index, is reported clean at exit 0 - the same shape this change closes elsewhere. It is pre-existing and not a regression, and it is disclosed rather than closed, because covering it means reconciling against a second pathspec derived from the link target. So the closure is stated as "within the declared roots, as git names them" and never as a universal over any corpus.

A count of what the sweep opened does not close this, which is why the second rule reads the index rather than a total: an emptied root contributes zero and a total still looks like a total. Only naming the corpus from a source outside the walk separates "read it and found nothing" from "never opened it". The expected set mirrors the walk's own admissions rather than inventing a second boundary, and the ignore rule is stated exactly rather than in its short form: `git check-ignore` consults the index by default, so it answers not-ignored for a path that is tracked even when a rule names it, which means the walk scans a tracked-and-ignored file and this check correspondingly refuses when one is missing. Both halves of that pair are asserted.

Two consequences are deliberately left open, measured rather than assumed, and both a scope decision rather than this one: a tracked file directly under `test/` is enumerated by neither route, and an index entry at exactly a scan root's own path matches no staged-route clause, because every clause tests a `<root>/` prefix. Neither is closed by the reconciliation above, and the reason is worth stating because it reads as though it should be: the reconciliation compares the walk against the index within the declared scope, so a path nothing declares in scope is absent from both sides of the comparison. Widening the scope is a change of its own, because enumerating those files buys only the common-shapes floor: they are TypeScript sources whose fixtures are string literals, so the segment-aware person-name, date-of-birth, phone and service-date recognisers never run on them. Name that floor as three detectors and never as two: a draft said "the dashed-SSN and email floor" and it was measured false, because the undashed nine-digit SSN recogniser carried on a reference qualifier is not segment-aware either and fires on a bare string literal exactly as the other two do. The two-detector wording understated the deferred scope by precisely the shape a dashed-SSN pattern cannot see. Widening the enumeration and widening the recogniser are two sides of it, each in addition to the other and neither instead of the other.

One behaviour outside a git checkout changed, and it is stated rather than buried: run where `git ls-files` cannot answer, the sweep now refuses at exit 2 instead of reporting clean, because "git could not tell me" and "git told me there is nothing" are the two answers this check exists to keep apart. `scripts/` is not in the published tarball, so every caller is inside a checkout of this repository.

🩺 BREAKING for `build277` callers: an X212 277 emitted with a service line was short a required element, and every 277 read discarded the submitted units (`X12-277-SVC07-NOT-DECODED`).

`get277Status` read the Loop 2220 `SVC` segment as far as SVC-04 and stopped, and `build277` emitted exactly those four elements. SVC-07, the units of service count (X12 element 380, Quantity), is usage **R** in TR3 `005010X212`, so **every X212 277 this library produced with a service line was non-conformant on the wire**, and the count a submitter sent never reached the model on the way back in.

Both directions now carry it, as `X12ServiceLineStatus.unitsOfService` and `Build277ServiceLineSpec.unitsOfService`. It decodes as an `X12Decimal` like every other quantity here and never via `parseFloat`; `undefined` still means "not decoded" rather than "absent", and a present-but-undecodable SVC-07 raises `X12_UNPARSEABLE_DECIMAL` at `position.elementIndex` 7 while an absent one raises nothing. The warning registry is unchanged.

**`build277` now refuses a service line with no `unitsOfService`**, with the existing `ClaimStatus277BuildError` and code `X12_277_BUILD_INVALID_SPEC`, raised as a precondition before any segment is built. Its message names SVC-07, the TR3, and the structural locator of the line, with no member id, name, trace or claim id. **The count is never defaulted.** A quantity the caller did not supply is a quantity nobody sent, and a units figure is one a payer reprices against, so inventing a `1` would put data on the wire that no submitter stands behind. If you emit X212 277s with service lines, the first build after upgrading throws until you supply the submitted count.

**`build277CA` is deliberately unaffected.** In `005010X214` the same element is usage **S**, so the identical spec still builds and simply omits it. That asymmetry is the shape of the fix, not a gap in it. Usage was read from the pyx12 005010 maps (`277.5010.X212.xml`, `277.5010.X214.xml`), outside this repository, rather than from this library's own reader.

**SVC-05 stays unread on the 277, on purpose.** It is usage N in both 277 TR3s. On the 835 it is the Units of Service **Paid** Count and is read; reading it on a 277 for symmetry would put a quantity on the model that no 277 sender ever wrote.

**Read the scope literally: this fixed ONE element's usage, and it does not make an emitted service line conformant.** It was not a 277 usage audit, and no census of what remains is published here, on purpose. Other required elements of the same `SVC` are still unguarded, and finding another is expected rather than a new defect. To name two: `SVC-01` and `SVC-02` are both usage R in X212 and both are optional on `Build277ServiceLineSpec`, so a line supplying only `unitsOfService` emits `SVC*******1~` with no refusal. The missing guard is what is pre-existing, not that byte string: at base the same spec emitted a bare `SVC~`, because the SVC-07 slot did not exist. `SVC-03` is usage R in X212 and usage N in X214 and is optional in both builders. And the read side still raises no warning for an X212 277 that arrives with no SVC-07, since a lenient reader saying so needs a new Tier-2 registry code. All of it is pre-existing; widening the guard would have turned this slice into that audit, and it is its own item. `KNOWN-LIMITATIONS.md` carries the same statement.

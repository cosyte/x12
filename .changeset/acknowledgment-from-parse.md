You can now derive the TA1 and the 999 you send back from what `parseX12` found, instead of assembling them by hand. `deriveTA1Spec(interchange)` returns a `buildTA1` spec that echoes ISA-13, ISA-09 and ISA-10 and accepts, or rejects with the TA1 note for the first envelope finding: `001` for an ISA-13 and IEA-02 that disagree, `021` for an IEA-01 that miscounts the groups, `023` for a missing IEA, `024` for a segment outside every transaction set, `026` for an ISA element carrying the element separator. `derive999Spec(interchange, { envelope, groupIndex })` returns a `build999` spec for one functional group: AK1 and each AK2 echo the group and its transaction sets, IK5 rejects a set with no SE (`2`) or whose SE-02 does not match ST-02 (`3`), an IK3 and IK4 locate a dangling release character or a BDS or BIN length that does not frame (IK5-02 `5`), a TA1 inside a transaction set is an unexpected segment (IK3-04 `2`), and AK9 rejects a group with no GE (`3`), a GE-02 that does not match GS-06 (`4`) or a GE-01 that miscounts (`5`). Both return `reported` and `unreported` beside the spec, so every warning in scope is accounted for. The new `ACK_WARNING_MAPPINGS` table names, for every warning code, the code each acknowledgment carries for it, or why it carries none. We report only the envelope and base-standard syntax the parser checks, never implementation guide usage, and SE-01 is not checked against the segment count. Nothing changes for existing callers; the new "Acknowledge an interchange" guide and `examples/acknowledge-from-parse.ts` show the calls.

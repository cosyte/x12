Refuse a non-string element value in every builder instead of emitting it as an empty element, and stop `escapeRelease` returning `""` for a non-string.

`escapeRelease` opened with `if (value.length === 0) return value;` and then looped to `value.length`. On a number `.length` is `undefined`, so the early return did not fire, `i < undefined` was false, the loop body never ran, and it returned its empty accumulator: the value vanished with no warning and no error. The types say `string`, so a TypeScript caller could not reach it; a JavaScript or JSON-driven caller could. Measured at `0.0.8` on an otherwise valid `build835` spec with only `patientControlNumber` changed to a number, it emitted `CLP**1*500.00*450.00*50.00*MB*ICN-9001*11::1` with `ix.warnings.length === 0` and a frozen, successful-looking interchange. CLP-01 is required by TR3 005010X221A1 Loop 2100 and is the key that reassociates the remittance back to the 837's CLM-01. The builder's own `patientControlNumber === ""` guard did not catch it, because the value was not yet a string when it was checked. The same one line reached every escaped slot in all nine builders, including the 837's own CLM-01.

All nine builders now take their `esc` helper from `makeCallerEscaper`, which type-checks the value and refuses with the calling module's own typed, code-tagged error (`X12_835_BUILD_INVALID_SPEC` and its eight siblings). It refuses rather than coercing, on purpose: a JSON payload that carried `"0012345"` as a number has already lost the leading zeros, so `String(12345)` would emit a well-formed identifier that is not the one the caller sent, and a remittance that reassociates to the wrong claim is worse than one that fails to reassociate at all. `String(1e21)` is `"1e+21"` and `String(NaN)` is `"NaN"`, neither valid in an `AN`, `ID` or `Nn` element, and `X12Decimal` is already the sanctioned route for numeric content. No caller who was getting the value into the document is broken, because the numeric path did not work: it silently lost the field.

The exported `escapeRelease` now throws `TypeError` on a non-string rather than returning `""`, and a boxed `new String("…")` is refused where it built at `0.0.8`.

The guard is on the escape helper, not on emission, and three classes of slot do not go through it. All three are pre-existing, measured, unchanged here, pinned by the new suite and disclosed in `KNOWN-LIMITATIONS.md`. 36 `esc` slots read `.toString()` off what the types say is an `X12Decimal`, so a raw number arrives already a string and is passed through: a `patientResponsibilityAmount` of `0.1 + 0.2` still emits `...*0.30000000000000004*...`, `1e21` still emits `...*1e+21*...` and `NaN` still emits `...*NaN*...`, each with zero warnings. Seven string-typed positions never call the escape helper at all: the 999's `groupControlNumber` (GS-06 / GE-02), `transactionSetControlNumber` (ST-02 / SE-02) and `disposition` (AK9-01 and IK5-01), and the 278's `levelCode` (HL-03). And the fixed-width ISA / GS slots go through `pad` / `padControl`, so a number throws an untyped `TypeError` and a numeric `interchangeControlNumber` throws a typed refusal whose text misleadingly says "exceeds the 9-char spec limit".
